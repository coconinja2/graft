Part 2 — Parallel Agent Infrastructure

Graft: Runtime Resource Coordination for Parallel Coding Agents

You've parallelized your agents. You've isolated them with worktrees. Now they're stepping on each other mid-execution. This is the missing piece.

10 min read · AI Engineering · Multi-agent Systems

In the last piece, I mapped parallel agent execution onto classical concurrency primitives — race conditions, mutexes, semaphores, event buses. The thesis was simple: parallel agents are just multithreading at a higher abstraction layer, and the same problems show up.

That article got one question more than any other: "Okay, but what do I actually use?"

The honest answer, at the time, was: nothing. The tooling doesn't exist yet. You either hand-roll coordination logic into your agent prompts, accept occasional merge conflicts, or serialize your agents and give up on parallelism entirely.

So I built it. This is the writeup for Graft — a lightweight runtime coordination layer for parallel coding agents.

The Problem Worktrees Don't Solve

The standard advice for parallel agent deployments is: give each agent its own git worktree. Separate branches, separate working directories, no shared state. Agents work in isolation, you merge at the end.

This works until your agents need to touch the same files.

And they always eventually need to touch the same files. Shared types. The router. The database schema. Auth utilities. These are the connective tissue of a codebase — the files every feature reaches into. When four agents are building four features simultaneously, at least two of them will reach for src/auth/types.ts at the same moment.

Fig 1 — Three agents targeting the same shared file simultaneously with no coordination. Last write wins — which means you lose everyone else's changes.

Worktrees don't help here. Each agent is in its own branch, writing its own version of auth/types.ts. When you merge, you resolve three-way conflicts manually — which defeats the point of running agents in parallel in the first place.

The missing primitive is a runtime claim: a way for an agent to say "I am about to touch this file" and for every other agent to be told "wait, or find another approach" before it writes.

What Graft Does

Graft is a local coordination bus. It runs as a lightweight process alongside your agents and exposes a simple HTTP API. Before any agent touches a shared resource — a file, a database, a port — it sends a claim request to the bus. The bus either grants the claim (resource is free) or returns information about who holds it and why.

Agents also publish signals mid-execution: typed events that carry context to other agents. If Agent A discovers that an interface it's modifying is used by Agent B's target file, it publishes a signal. Agent B receives it at the next tool boundary and adjusts.

"No orchestrator. No agent-to-agent communication. Just a bus, a claim registry, and a config file that defines how agents respond to signals."

The whole design is deliberately narrow. Graft doesn't orchestrate, assign tasks, manage lifecycles, or persist work. It does one thing: coordinate concurrent access to shared resources at runtime.

Fig 2 — With Graft, every write attempt routes through the claim registry. Agent-a gets the resource; agents B and C receive structured context about why they're blocked and what to do next.

How It Works

The Hook Integration

For Claude Code, Graft installs as a pair of hooks that fire at every tool boundary — the moment between the LLM deciding to write a file and the write actually happening:

# .claude/settings.json
{
  "hooks": {
    "preToolUse": "graft hook pre --tool $TOOL_NAME --input '$TOOL_INPUT'",
    "postToolUse": "graft hook post --tool $TOOL_NAME --output '$TOOL_OUTPUT'"
  }
}

The preToolUse hook fires before every Write, Edit, Bash, or NotebookEdit call. It extracts the target resource from the tool input, hits the bus's /claims endpoint, and either passes through (claim granted) or returns a structured block message to Claude with the holder's identity, intent, and any pending signals from the bus.

The postToolUse hook refreshes claim TTLs on write and releases claims on read completion. If the bus is unreachable, both hooks fail open — the agent logs a warning and proceeds normally. A crashed bus should never crash a running agent fleet.

Claims

// Agent A — attempting to write auth/types.ts
const claim = await graft.claim({
  resourceId: 'src/auth/types.ts',
  intent: 'adding OAuth provider fields to AuthConfig',
  ttl: 120
})

if (claim.granted) {
  // safe to write
  await writeFile('src/auth/types.ts', newContent)
  await graft.release('src/auth/types.ts')
} else {
  // held by agent-b: "adding rate limiting fields"
  // respond per graft.config.yaml signal_responses
  console.log(`Held by ${claim.holder.agentId}: ${claim.holder.intent}`)
}

Every claim has a TTL. If an agent crashes mid-execution, its claims expire automatically — the cleanup loop runs every 10 seconds. No stuck locks, no manual intervention required.

Signals

Signals are typed mid-execution events that propagate context across agents. When Agent B discovers that the interface it's modifying is depended on by another feature, it publishes a signal:

await graft.publish({
  type: 'interface_change',
  message: 'AuthConfig now requires timeout: number — update call sites',
  affectedResources: ['src/auth/types.ts'],
  severity: 'medium'
})

Every other agent polls for pending signals at each tool boundary. The response strategy is configured in graft.config.yaml — not hardcoded. An interface_change might trigger checkpoint_and_replay; a security_finding might trigger escalate_to_human. The policy is yours.

Fig 3 — Signal propagation. Agent-b publishes at a tool boundary. The bus queues the signal. Agents A and C receive it at their next tool call, before they act.

The Configuration

All policy lives in graft.config.yaml. The bus reads it at startup. Agents read it to know how to respond to incoming signals. No hardcoded behavior anywhere.

bus:
  port: 7433
  backend: memory   # or redis for persistence

agents:
  claim_ttl: 120    # seconds before abandoned claim expires
  heartbeat_interval: 30

signal_responses:
  interface_change:   checkpoint_and_replay
  security_finding:   escalate_to_human
  schema_change:      checkpoint_and_replay
  resource_conflict:  wait_and_retry
  new_utility:        incremental_adjust

pools:
  test_database:
    resources:
      - postgres://localhost:5432/test_1
      - postgres://localhost:5432/test_2

The pools section handles another common problem: resource scarcity. When four agents all need a test database simultaneously, Graft manages a pool and allocates resources like a semaphore — agents acquire from the pool, run their tests, release back.

What Graft Is Not

Important scope constraints. Graft deliberately does not orchestrate agents, assign tasks, manage lifecycles, persist agent work, provide monitoring UI, or implement planning protocols. It is a coordination layer only. Use it alongside git-stint for branch management, scout-and-wave for upfront dependency planning, and Galactic for environment management.

The design constraint I kept coming back to: if the bus goes down, agents should keep working. Graft is infrastructure, not a hard dependency. Every SDK call fails open. A crashed bus logs a warning and lets agents proceed. This is non-negotiable.

Getting Started

# Install
npm install -g graft

# Start the bus
graft start

# Hook into Claude Code
graft install --claude-code

# Monitor claims and signals in real time
graft status

The CLAUDE.md file — the full build specification including architecture, file layout, and build order across five phases — is available in the project repository. If you want to contribute to the implementation or build the bus yourself from the spec, start there.

Why "Graft"

We went through a lot of names: Baton, Seam, Knot, Cinch. Graft stuck because it captures both sides of what this tool does. In surgery, grafting means joining tissue from two sources into one living system — distinct origins, unified function. In development slang, it means doing the actual unglamorous work of making things fit together.

Parallel agents are powerful. Coordination is the work that makes them actually useful. That's what Graft is for.
